# 대사와 비텍스트 경계 검증

2026-09-09. 현재 확인 대상은 v1.1a-dev08이다. 전편 플레이 또는 100% 번역 완료를 뜻하지 않는다.

## 스크립트 구조

`source/dialogue_profile.json`은 EC69A4..EC7944의 1000개 포인터와 각 스크립트의 원본 해시를 고정한다. C7B18은 인덱스에 따라 이 표를 읽고, C73E0은 그 포인터를 문맥 구조 +10에 저장한다. C6F58은 그 포인터에서 8-byte 명령을 읽으며 opcode31에서 끝난다. 다음 EC7944는 별도 화자 조회기가 읽는 표다.

- opcode0F: 5156개. 명령 +4가 C7550/C7668로 전달되는 대사 포인터다.
- opcode25: 52개. C79C0이 화자 표시 방식을 바꾼 뒤 같은 C7550을 호출한다. 실제 로이드 소개 장면에서 이 경로를 확인했다.
- 합계 5208개 대사 항목, 고유 원문 위치 4788개. 모든 K1.1 항목의 디코딩→인코딩이 원래 바이트와 일치한다. 그대로인 12개도 빈 문자열·문장부호로 보존한다.

최초 5156개 집계는 opcode0F만 포함한 조사였다. 소개 장면을 직접 확인하면서 opcode25를 추가했으며, 첫 집계를 전체 대사 수로 확정하지 않는다. 이 표 밖 UI·설명·그래픽은 별도 모집단이다. 표에 저장되었다는 사실과 실제 플레이에서 모든 항목에 도달했다는 주장을 구분한다.

## 수정 범위

현재 228개 항목을 고정된 원문·명령과 대조해 수정한다. 218개는 일본어 원문에서 같은 인물이 확인되는 승인 이름 표기이며, 끝소리가 바뀌는 콜레트·채트·킬의 조사도 확인했다. 나머지 10개는 선박 번호·호 누락, 하드코딩된 선박 이름, 빠진 이름 치환 기호, 목적지 안내 누락, 인물/층수 불일치 등 개별 수정이다.

새 게임 선박 이름은 어간 `드림`으로 저장한다. 기존 `@D호` 대사에 `드림호`를 넣던 개발판의 중복을 실제 화면에서 확인해 수정했다. 사용자 저장 이름은 자동 변경하지 않는다.

## 문자 경계와 이름 치환

원래 C7668은 256 bytes를 할당하고 `@0/@1/@B/@G/@D/@K/@L`을 처리한다. 그런데 문자 경계를 확인하지 않고 바이트를 순회하므로, 두 바이트 공백 `8140` 바로 뒤의 ASCII `B`가 `@B`처럼 처리된다. K1.1의 18FB34·190320 두 대사 항목에서 이 현상을 실제 원본 CPU 처리기로 재현했다. 원문은 레미유적 지하 2층이므로 해당 두 표기를 풀어 써서 충돌을 없앴다.

`dialogue_tokens.py`는 문자 경계에서 제어 기호를 읽고, 생성 문장에 원래 엔진이 오인할 바이트 조합이 있으면 빌드를 막는다. 메르디 지하 1층 수정 초안도 이 검사에 걸려 dev06은 ROM 생성 전에 중단되었다. 숫자 표기를 수정한 dev07 이후 검사를 통과한다. 실패 산출물 폴더는 보존한다.

## 실제 처리기 검사

dev08의 `dialogue-resource-verification.json`:

- 1000개 스크립트의 명령·화자·비텍스트 인자 보존. 선언한 대사 포인터 228개만 수정.
- 5208개 대사 × 기본/최대 5한글 이름 조건 = 10416회 원래 이름 처리기 실행.
- 검사 조건에서 최대 출력 178 bytes, 할당 256 bytes. 문장 끝과 앞뒤 보호 바이트 보존.
- 수정한 228개 항목은 별도로 가나·ASCII·혼합 이름까지 1145회 검사.

메모리 할당기만 시험용으로 대체했으며 이름 처리와 문자열 길이 계산은 실제 ROM 코드를 실행했다. 실제 스크립트의 모든 분기, 장면 배치, 가능한 모든 사용자 문자열, 전편 도달 검증과는 다르다.

## 요리 표

74C67C..74C834는 20-byte × 22개 요리 표다. 97C8의 인덱스 조회, A6BAC의 22개 메뉴 개수, D81BC의 소형 이름 +4, D839E의 큰 이름 +0, 9AFA의 설명 +8을 확인했다. +C..13의 효과·재료 바이트는 번역 대상이 아니다.

소형 이름 22개와 명확한 큰 이름 오역 4개·설명 오역 3개, 총 29개 문자열 필드를 수정했다. `verify_recipes.py`는 원래 조회 및 목록 출력 경로를 두 모드에서 44회 실행하고, 효과·재료 바이트 보존을 확인한다. 실제 요리 수행과 결과 화면 검수는 별도로 남아 있다.
