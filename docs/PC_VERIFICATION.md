## 저장 파일 차이 조사

EEPROM 원시 바이트는 8-byte 전송 단위로 순서가 뒤집힌다. 복원된 첫 저장 블록은 `NARIKIRI`, +8의 `0131CD45`, +C의 합계 검사값, +9DC의 플레이 시간으로 구성된다. 실제 `08008900/080089D4/08008A08`이 +10..F00의 32-bit 합계를 기록·검사한다. `08008C08`은 `03002BC8`의 실시간 카운터를 버퍼+9DC에 복사한다.

앞선 같은 ROM의 두 코어 저장은 시간 3프레임과 그 검사값만 달랐다. 정상 저장 확인 직전에 컨트롤러 대기 3프레임을 추가하자 저장 파일 전체 8192 bytes가 mGBA 기준과 일치했다. 근거: `output/pc-vba-timer-cause-05/timing-causality.json`. 따라서 전체 저장 해시를 임의 갱신하지 않고, 게임 자체 검사값과 시간 이외 전체 상태를 검사하도록 바꾸었다. 허용 시간차는 관찰된 ±3프레임까지만이며 실제 값도 보고한다.

`tools/save_contract.py`는 본체 변조, 검사값을 다시 계산한 상태 변조, 허용 범위를 넘는 시간을 각각 거부하는 것을 확인했다. 이 첫 저장 회귀 규칙은 임의의 사용자 저장을 검사하는 범용 규칙이 아니다.

## 검증 도구에서 수정한 오류

VBA Next의 139264-byte 노출 버퍼는 128 KiB Flash 영역 다음에 8 KiB EEPROM이 있다. 처음에는 EEPROM을 앞부분에 넣어, 저장 생성은 성공하지만 이어하기가 새 게임으로 진행되는 캡처가 나왔다. `libretro/vba-next@788192f215ad0a1413f1625b40ebba3423fa0ade`의 `retro_init`과 `eepromData`를 대조하여, 해당 정확한 코어 해시의 가져오기·내보내기를 +20000으로 통일했다. 수정 전 실패 캡처는 보존했다. 이는 ROM 결함 수정으로 집계하지 않는다.

# dev30 의상 변경 후 중단 저장 추가 확인
