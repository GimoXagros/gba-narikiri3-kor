# 한글 이름 입력과 검증

v1.1a-dev14에서 한글 입력 후보판을 추가했다. dev15는 같은 후보판에 특기 해제/빈 저장 안내 번역을 포함한다. 전편 검증 완료를 뜻하지 않는다.

## 표시와 입력의 분리

원작의 D63E0은 6개 행 포인터를 읽어 표시하지만, D6470은 별도의 입력 표를 읽는다. 표시 문자열만 바꾸면 보이는 글자와 저장 글자가 달라진다. `source/name_keyboard_profile.json`은 원래 코드, 입력/표시 표, 문자열, 좌표 범위를 해시로 고정한다.

한글 2350자는 15열 × 6행의 27페이지다. 이어서 영문, 가타카나, 히라가나 페이지가 있다. L/R과 오른쪽 전환으로 양방향 순환한다. 원작의 가나/탁점/영문 입력 함수와 후보 바이트는 유지한다. 일본어 입력용 글자판은 번역 누락 문구와 구별한다.

마지막 한글 페이지의 빈 80칸은 선택해도 이름을 늘리지 않는다. 이름은 기존 4 bytes × 5칸이다. 입력·삭제·확정·대형 글자 변환·저장 레이아웃을 확대하지 않는다. 한글 입력은 완성형 선택이며 자모 조합 방식이 아니다.

212-byte 입력/표시 코드는 확장 영역 09000800에, 후보 셀은 090B0000, 행 포인터는 090B2000, 제목 포인터는 090B2400, 문자열은 090B3000 이후에 배치한다. 기존 09000400 가져오기와 09001000 글꼴을 침범하지 않는다. 빌더가 충돌과 선언 밖 변경을 거부한다.

## CPU 검사

`verify_name_keyboard.py`는 실제 Thumb 코드를 실행한다.

- 두 글꼴 모드에서 30페이지를 정방향/역방향으로 계속 그린다. 기존 이름을 유지한 상태로 9400개 후보 글꼴 픽셀을 확인한다.
- 2350자 × 5칸 × 2모드의 23500개 입력·확정·삭제 사례를 검사한다.
- 원래 영문/가나 270칸 × 2모드의 입력 결과를 K1.1과 비교한다.
- 빈 칸, 잘못된 좌표/페이지, 여섯 번째 입력 168개와 원래 페이지 조작 180개를 검사한다. 페이지 검사에서 관련 없는 소리 재생 함수만 대체한다.
- 이 화면의 최대 동시 캐시 사용은 103칸이다. 전체 게임의 124칸 캐시 한도 검증으로 확대하지 않는다.

## PC 정상 입력과 저장

dev14의 mGBA/VBA Next에서 새 게임부터 버튼만으로 30페이지를 양방향 순환했다. 입력 이름 보존, 삭제, 빈 칸 무시, 다섯 글자 제한을 읽기 전용 관찰로 확인했다. 검증용 이름은 `가A나B힝`, `한글이름값`, 배 이름 `가나다라마`다.

실제 대사에서 `가나다라마호`가 출력되는 것을 확인했다. 게임에서 저장한 뒤 별도 프로세스로 다시 불러와 이름과 팀/레벨/HP를 관찰했다. 여섯 개 이름 필드(+28/+3B/+48/+5B/+68/+7B)는 원래 04D00 변환기로 계산한 값과 일치했다. 이 분리 계산에서는 373C 임시 할당만 대체하고 13-byte 경계를 검사했다. 두 코어 모두 재실행 후 EEPROM이 입력 저장과 8192 bytes 모두 동일했다.

저장 SHA-256:

- mGBA: `36707dea4b57f414f15e7275240d3ee3bec74a6661a3ab0b1c0822507d7b39de`
- VBA Next: `d2781de1d02cab4a0ec1ed6b3c373a711cb45d6a81d0e64781d0690f29d1d501`

`qa/traces/custom-name-first-save.jsonl`에 실제 조작을 보존한다. 최초 기존 짧은 이름용 입력을 이어 붙인 시도는 옷 메뉴로 진행되어 저장 전 FF EEPROM을 내보냈다. 실제 저장 확인/완료 화면을 거친 후 별도 파일을 만들었으며, 앞선 미저장 파일을 성공으로 집계하지 않았다.

긴 조작 경로의 저장은 기본 이름 회귀 경로와 이름/시간/검사값 외에 +AB7도 10→00으로 달랐다. 이 바이트를 임의로 정상화하지 않았다. 옷 메뉴 진입만으로 설명되는지 대조했지만 재현되지 않았다. 서로 다른 입력 경로의 진행 상태가 같다고 주장하지 않으며, 원인 추적은 남아 있다. 이름 필드 자체와 새 프로세스 재로드 후의 전체 저장 일치는 별도로 통과했다.

## 도입부 시간 회귀

기본 이름으로 같은 기존 입력을 재생한 dev15 저장은 이름을 포함한 전체 상태가 종전과 같고 시간/검사값만 달랐다. mGBA의 저장 시각은 17768→17733이다. 매 입력 경계의 관찰에서 첫 후보판(frame7098)에서 -16, 배 후보판(frame7878)에서 -32가 되었고, 이후 메뉴/빈 저장 안내 표시에서 저장 직전 -35가 되었다. 이 코드는 원작의 프레임 대기/시간 루틴을 수정하지 않는다.

VBA Next의 같은 dev15 관찰값은 17728이다. 기존 ±3 범위를 무조건 넓히지 않고, ROM·코어·입력 해시가 모두 일치하는 `source/opening_timing_profile.json`에서 각각의 관찰값을 정확히 요구한다. 새로운 빌드가 이 해시와 다르면 이 기준을 자동 적용하지 않는다. 오디오나 실시간 성능의 동일성을 뜻하지 않는다.

남은 범위는 다른 이름 변경 경로, 모든 대사에서의 최대 길이 레이아웃, 장시간 진행/모든 저장/전체 캐시 생명주기다.
