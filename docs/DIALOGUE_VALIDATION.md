## 스크립트 구조

`source/dialogue_profile.json`은 EC69A4..EC7944의 1000개 포인터와 각 스크립트의 원본 해시를 고정한다. C7B18은 인덱스에 따라 이 표를 읽고, C73E0은 그 포인터를 문맥 구조 +10에 저장한다. C6F58은 그 포인터에서 8-byte 명령을 읽으며 opcode31에서 끝난다. 다음 EC7944는 별도 화자 조회기가 읽는 표다.

- opcode0F: 5156개. 명령 +4가 C7550/C7668로 전달되는 대사 포인터다.
- opcode25: 52개. C79C0이 화자 표시 방식을 바꾼 뒤 같은 C7550을 호출한다. 실제 로이드 소개 장면에서 이 경로를 확인했다.
- 합계 5208개 대사 항목, 고유 원문 위치 4788개. 모든 K1.1 항목의 디코딩→인코딩이 원래 바이트와 일치한다. 그대로인 12개도 빈 문자열·문장부호로 보존한다.

최초 5156개 집계는 opcode0F만 포함한 조사였다. 소개 장면을 직접 확인하면서 opcode25를 추가했으며, 첫 집계를 전체 대사 수로 확정하지 않는다. 이 표 밖 UI·설명·그래픽은 별도 모집단이다. 표에 저장되었다는 사실과 실제 플레이에서 모든 항목에 도달했다는 주장을 구분한다.

## 문자 경계와 이름 치환

원래 C7668은 256 bytes를 할당하고 `@0/@1/@B/@G/@D/@K/@L`을 처리한다. 그런데 문자 경계를 확인하지 않고 바이트를 순회하므로, 두 바이트 공백 `8140` 바로 뒤의 ASCII `B`가 `@B`처럼 처리된다. K1.1의 18FB34·190320 두 대사 항목에서 이 현상을 실제 원본 CPU 처리기로 재현했다. 원문은 레미유적 지하 2층이므로 해당 두 표기를 풀어 써서 충돌을 없앴다.

`dialogue_tokens.py`는 문자 경계에서 제어 기호를 읽고, 생성 문장에 원래 엔진이 오인할 바이트 조합이 있으면 빌드를 막는다. 메르디 지하 1층 수정 초안도 이 검사에 걸려 dev06은 ROM 생성 전에 중단되었다. 숫자 표기를 수정한 dev07 이후 검사를 통과한다. 실패 산출물 폴더는 보존한다.

## dev30 퍼센트 출력 결함과 전수 표시

위 전수 검사에서 남았던 항목은 스크립트 240의 대사 레코드 15AC34다. 기존판 문자열은 `９７．３%의`에서 ASCII `%`를 사용한다. 원래 포맷 처리기 25CC가 이어지는 한글까지 제어 인수로 소비하여 실제 출력은 `９７．３　확률로　틀려`가 된다. 일본판은 원래부터 전각 `％`(8193)를 써서 정상 표시된다. 같은 CPU 소비자와 버퍼에서 일본판/기존 1.1/수정판을 비교하고 직접 픽셀을 확인했다. 근거는 `analysis/generated/literal-percent-three-way-30.json` 및 같은 이름 PNG다. 정상 스토리 장면 캡처와 구분한다.

dev30은 이 한 글자를 전각 퍼센트로 고치고, 앞으로 ASCII 퍼센트가 명시적인 `%k/%l` 이외에 들어오면 빌드를 거부한다. 이 두 명령은 확정한 5208개 대사 모집단에서 확인한 명령이다. 일본판·기존판의 포맷 처리 코드는 수정하지 않았다.
